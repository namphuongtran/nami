# Nami Pre-GA Ratification Checklist

Every accepted ADR builds a **mechanism**; several defer a **policy, threshold, or sign-off** to a human owner (DPO, Legal, Security, Ops, Product) before general availability. This file consolidates those into one release gate. The ADR remains the source of each decision; this is the tracking index. **GA is blocked until every item below is ratified** (recorded with date and approver). Interim values may ship in pre-GA builds where an ADR marks them interim. This project builds mechanisms and does not itself assert legal compliance.

**Status key:** ☐ open · ☑ ratified (date, approver)

## DPO / Legal

- ☐ Audit: minimum event catalog, retention window, PII-redaction policy, SIEM/WORM destination ([ADR-0008](adr/0008-audit-subsystem.md))
- ☐ Erasure: whether crypto-shred satisfies Art.17; audit retention plus per-record Art.17(3) basis; legal-hold workflow; anonymise-in-place interpretation; Recital-66 replica retention ([ADR-0016](adr/0016-right-to-erasure.md))
- ☐ Data-subject rights: Art.12 SLAs; Art.15 source/automated-decision wording; portability direct-transmit yes/no; Art.34 high-risk threshold plus jurisdiction authority/deadline; Art.30 content; DPIA execution; consent policy-version governance; Art.18 scope plus Art.21 legitimate-interest balancing ([ADR-0053](adr/0053-data-subject-rights-suite.md))
- ☐ Cross-border / residency: per-tenant residency classification; lawfulness and mechanism of each transfer; transfer-assessment content and filing; Law-on-Data core/important-data export path if applicable ([ADR-0054](adr/0054-cross-border-transfer-and-data-residency.md))
- ☐ Source-address pseudonym in the audit lane: whether persisting `SourceIpHash`, a keyed untruncated HMAC over the request address, is acceptable under the applicable basis. The architecture is decided and the legal question is deliberately not: the field is nullable and its emission configurable, so a refusal is a configuration answer. **Detection does not depend on this**, because per-address evaluation runs in a bounded in-memory window that stores nothing, so a refusal costs durable cross-node *attribution* and not the capability. **Bounded here is measured, not asserted**: the design corpus's spike A-11 held the window at its ten-thousand cap across two million distinct addresses (verification record V30, 2026-07-29), which matters to this decision because an unbounded window would have made the fallback worse than the thing it replaces ([ADR-0082](adr/0082-abuse-detection-lanes-and-grouping-keys.md), with [ADR-0083](adr/0083-abuse-detection-is-built-in.md))
- ☐ Telemetry / registration: telemetry data categories (no PII); registration PII retention; privacy notice; registration terms ([ADR-0032](adr/0032-usage-visibility-and-licensing-posture.md))
- ☐ HIBP breach-check: sending a hash prefix to an external service (DP.01) ([ADR-0028](adr/0028-user-management.md))
- ☐ Consent re-prompt cadence: whether a granted consent must expire and be re-asked periodically. ADR-0004 deliberately leaves consent lifetime unbounded (an OpenIddict permanent authorization persists until the user revokes it), so bounding it is a policy call, not a build gap. If it is required, the mechanism is an expiry stamped on `Authorization.Properties` plus a prune ([ADR-0004](adr/0004-refresh-token-posture.md))
- ☐ Deprovision key-escrow retention window and residency ([ADR-0017](adr/0017-tenant-provisioning-and-silo-migration.md))
- ☐ Change-event publishing (v2): PII in event payloads flowing to the broker and its consumers, the outward data flow, and event retention (DP.01) ([ADR-0071](adr/0071-identity-change-event-publishing.md))

## Security

- ☐ Break-glass (key compromise): authorized-personnel list; multi-node reload/cache-evict automation ([ADR-0007](adr/0007-key-compromise-break-glass-runbook.md))
- ☐ Admin break-glass (ISMS DP.01): custody, rotation cadence, unseal second-approver, alert recipients, network allow-list, drill cadence, FIDO2/CBA upgrade ([ADR-0015](adr/0015-admin-break-glass-and-first-admin-bootstrap.md))
- ☐ Secret-store: break-glass purge holder; two-approver process; per-cloud adapter capability matrix ([ADR-0009](adr/0009-secret-store-access-and-rollover.md))
- ☐ Delegated-admin: initial capability taxonomy; ReBAC-adoption timing ([ADR-0010](adr/0010-tenant-hierarchy-delegated-admin.md))
- ☐ MFA / assurance: AAL threshold per dangerous capability; per-scope required-`acr` list ([ADR-0013](adr/0013-mfa-assurance-and-step-up.md))
- ☐ Abuse **detection** rule set: the window, threshold, severity and grouping key for each built-in rule (credential stuffing, brute force on one account, lockout-DoS, second-factor failure spike, issuance spike per client or tenant, `invalid_client` spike, per-address velocity, unknown-source keyring access). Distinct from the **enforcement** caps under Product / Ops below: those answer "what do we refuse", these answer "when do we page", and a threshold invented in an ADR would be a security decision disguised as an architecture constant ([ADR-0083](adr/0083-abuse-detection-is-built-in.md))
- ☐ Credential-hardening thresholds: length 12, PBKDF2 >= 210k (with DPO on HIBP) ([ADR-0028](adr/0028-user-management.md))
- ☐ Accepted risk: Pool-shared keyset (pool-group blast radius) ([ADR-0033](adr/0033-key-scope-isolation-model.md))
- ☐ Browser-facing header residuals: the enumerated `Permissions-Policy` allowlist, which ADR-0091 fixes only as a deny-by-default posture because the concrete feature identifiers depend on what the passkey path needs; and acceptance of `img-src 'self' https:` on the login page, which admits any https origin as an image source so tenant and client logos render, rather than proxying them through Nami and widening the SSRF surface that the render-time logo guard exists for. The framing, script, and style directives need no ratification: each is `'none'` or `'self'` with a startup invariant behind it ([ADR-0091](adr/0091-browser-facing-response-headers.md), with [ADR-0028](adr/0028-user-management.md) for the passkey feature list)
- ☑ How the UI response profile reaches pages Nami did not write (**2026-08-02, Nam Phuong Tran as security lead**; recorded as [ADR-0091](adr/0091-browser-facing-response-headers.md) parameter K and a third [ADR-0043](adr/0043-security-hardening-invariants-startup-check.md) invariant). The item read: [ADR-0027](adr/0027-packaging-and-distribution.md) parameter G ships no UI package, so an embedder writes their own login page, and the UI profile is selected by a `SecurityHeadersAttribute` that reaches only the pages it is applied to; the failure mode is a third party's login page served with no policy while every ADR-0043 startup check still passes, since those checks assert what the profiles contain and not which pages receive them. **Ratified as: the header middleware writes a profile on every response, endpoint metadata only selects which one, absent metadata means the UI profile, and leaving the policy requires an explicit opt-out**, with a `response-headers-registered` startup row for the consumer who never registers the middleware at all. Two things are worth carrying forward from how it closed. **The item as written located the fault in the wrong place**: the attribute's reach is the second-order effect, and the first-order fact is that ADR-0091 parameter B's three `Applies to` cells all enumerate surfaces Nami authors, so the partition stopped being total on the day parameter G was accepted, which was the same day that ADR was. **And the three options offered here omitted the one this repository already had a precedent for**: they were documentation, a default, or a startup *warning*, while ADR-0043's `hsts-enabled-outside-dev` row had been asserting that a middleware **is registered** since 2026-07-26, making a startup *failure* available and unlisted. What is signed off is therefore not one of the three options as stated
- ☐ Audit-export bounds: whether an export has an absolute cap on rows or time span at all, and how far the row count may drift between approval and redemption before the ADR-0081 `query` guard refuses. This entry exists because a deferral was **lost on import**: the source corpus marks its guard-taxonomy decision "Accepted (Security to ratify the audit-export size threshold)", and neither ADR-0081 nor this checklist carried that, so the 90-day and 10k-row figures lived in four design documents with nobody obliged to sign them. Their original job, gating whether dual-control applied, is gone since ADR-0008 made every export dual-control, so what Security is ratifying now is a drift bound rather than a gate. Worth knowing while ratifying: any threshold of this shape is defeated by looping under it, and the same egress is reachable by paging `GET /audit`, so the bound is a drift control and not an egress control ([ADR-0008](adr/0008-audit-subsystem.md), [ADR-0081](adr/0081-dual-control-target-guard-taxonomy.md), design [15](design/15-admin-api.md))
- ☐ Formal cryptoperiod (ISMS sign-off, with Ops): the signing, encryption, and retention periods stated as policy with a named owner. The build implements ADR-0011's 90/14/14; this ratifies it as the recorded cryptoperiod ([ADR-0011](adr/0011-no-restart-key-rotation.md), [ADR-0005](adr/0005-encryption-credential-lifecycle.md))
- ☐ Authorization SLO / timeout (with Ops) ([ADR-0047](adr/0047-authorization-decision-engine.md))
- ☐ Trusted-proxy IP list for mTLS (with Ops) ([ADR-0014](adr/0014-advanced-protocol-scope.md))
- ☐ Change-event publishing (v2): per-consumer bus access control; whether configuring the broker connection is an IAM-class change requiring dual-control; thin-versus-fat payload for PII minimization ([ADR-0071](adr/0071-identity-change-event-publishing.md))
- ☐ BFF package shipped defaults: the cookie lifetimes the package ships (a sliding window plus an absolute cap, both consumer-tunable), which are legitimately allowed to exceed the OP's own 8-hour absolute session because the RP session is a separate object, so the number is a policy choice rather than a consequence of ADR-0003; and whether `POST` plus an antiforgery token replaces the session-bound `sid` query parameter as the shipped default on `/bff/logout`. Both ship to third parties who will not revisit them ([ADR-0029](adr/0029-bff.md), design [24](design/24-bff.md))
- ☐ Workflow-definition analysis, the one surface the five CI security scans do not reach: ADR-0092 pins SAST to the .NET SDK's own security rules, which see C# and nothing else, and the other four stages cover secrets, dependencies and the image but not what a GitHub Actions workflow does with untrusted input. ADR-0086 is adjacent and not the same question, since pinning every action by commit SHA constrains *which* code runs and not what an expression interpolates. Ratify this as an accepted risk, or decide that the stage is worth a sixth tool with a sixth licence to carry. The reason it is not an architect's pick is that the alternative to accepting it is adding a permanent dependency for the smallest of the five surfaces ([ADR-0092](adr/0092-ci-security-scan-tooling.md), [ADR-0086](adr/0086-pin-ci-actions-by-commit-sha.md))
- ☐ OWASP ASVS 5.0 Level 2 self-assessment coverage complete (L3 for key/token/dual-control/tenant-isolation), API Security Top 10 mapped ([ADR-0062](adr/0062-owasp-asvs-security-baseline.md))
- ☐ Independent penetration test: scope and rules of engagement agreed, a third party engaged, the test run against pre-production on synthetic data, and the findings ratified or accepted as risks. Scope covers the protocol endpoints, the admin API and admin application, tenant isolation (cross-tenant plus Pool shared keyset), and the break-glass paths; volumetric denial of service is out of scope ([ADR-0062](adr/0062-owasp-asvs-security-baseline.md), with [ADR-0033](adr/0033-key-scope-isolation-model.md), [ADR-0049](adr/0049-resource-server-per-tenant-validation.md), [ADR-0007](adr/0007-key-compromise-break-glass-runbook.md), [ADR-0015](adr/0015-admin-break-glass-and-first-admin-bootstrap.md))

## Ops

- ☐ **Row-level-security role verification in every deployed environment**: confirm the runtime database role is `NOSUPERUSER` and lacks `BYPASSRLS` ([ADR-0037](adr/0037-database-engine-postgresql.md)). This is the one isolation control that is neither in the code nor in the application's configuration, so the ADR-0043 startup self-check structurally cannot see it: a superuser connection satisfies every application-level check while silently disabling the row-level-security backstop entirely. The threat model rates the exposure Critical and classes it as a deployment control, which is why it is an Ops sign-off rather than a test
- ☐ Formal RTO/RPO targets, DR runbook, per-adapter capability matrix ([ADR-0006](adr/0006-disaster-recovery-key-material.md))
- ☐ Root-cert provisioning/rotation ceremony; per-environment cloud-protector adapter ([ADR-0012](adr/0012-key-bootstrap-and-dr-sequence.md))
- ☐ Public reference-host decision (owner / hosting / patch-cadence / cost) versus local-Docker-only ([ADR-0027](adr/0027-packaging-and-distribution.md))
- ☐ BFF ticket-store backing recommended by the reference sample (distributed cache versus database), which decides whether a BFF restart drops every session ([ADR-0029](adr/0029-bff.md), design [24](design/24-bff.md))
- ☐ Change-event publishing (v2): broker sizing, dead-letter policy, and alerting; confirm the single-stream topology once real tenant numbers exist ([ADR-0071](adr/0071-identity-change-event-publishing.md))
- ☐ Database HA: the concrete failover mechanism (self-managed cluster manager versus managed HA); whether Redis durability is enabled, given the quantified proof-replay window it closes and the write-durability cost it adds; the read-replica trigger threshold if that lever is ever adopted; failover-drill cadence ([ADR-0074](adr/0074-database-ha-and-cache-durability.md))
- ☐ Edge posture: the concrete L7 edge stack (WAF, CDN, or reverse proxy) assumed in front of the reference deployment, plus the trusted-proxy addresses or networks that forwarded-header processing and the mTLS carve-out both depend on ([ADR-0073](adr/0073-edge-posture-and-forwarded-headers.md), with [ADR-0014](adr/0014-advanced-protocol-scope.md) for the mTLS trusted-proxy list)

## Governance & launch (cross-cutting)

- ☐ Security disclosure window plus `security@` contact plus PGP key ([ADR-0045](adr/0045-security-disclosure-and-cve-policy.md))
- ☐ DCO versus CLA; self-govern versus software-foundation membership ([ADR-0046](adr/0046-governance-and-contribution-model.md))

- ☐ **Confirm the external-tool licences that the CI licence gate cannot see** ([ADR-0026](adr/0026-dependency-license-policy.md), [ADR-0078](adr/0078-load-test-tooling.md)). ADR-0026 section C's scan reads the NuGet restore graph, so **every external tool is invisible to it** and the gate's silence is not evidence of compliance. This is structural, not a bug to fix in the scanner. The tools in this class today are Apache JMeter (Apache-2.0) and the OIDF conformance suite image (MIT), each recorded with its verification source and date in [`DEPENDENCY-LICENSES.md`](DEPENDENCY-LICENSES.md). Legal confirms the list is complete for the distribution model and that none of these tools is conveyed inside a shipped artifact (the reference host image, the Helm chart, the NuGet meta-package, the `dotnet new` template), since bundling a tool changes the question from execution to conveying. **No AGPL or copyleft question remains open here**: k6 was removed for exactly that reason rather than carved out (ADR-0078), so this entry is an inventory confirmation, not a legal judgement call.
- ☐ **One IP-lawyer review of the public docs before public launch** (standing recommendation). In scope, among the rest: the architecture layer follows the **arc42** template's chapter sequence and credits it in [`docs/architecture/README.md`](architecture/README.md). arc42 is CC BY-SA 4.0, whose ShareAlike term attaches to adaptations of the licensed material; this repository reproduces none of arc42's text, explanations, or diagrams and adapts the chapter set, so the position taken is that the documents are not adaptations and remain Apache-2.0 with the credit given as attribution. That position is worth one lawyer's confirmation, not a redesign. **The same question applies to the detailed-design layer**, whose section sequence follows the **IEEE 1016** software-design-description viewpoints, credited in [`docs/design/README.md`](design/README.md). IEEE 1016 is a paid standard rather than an openly licensed one, so the position is narrower and worth stating: only the viewpoint vocabulary and the section ordering are used, no standard text is reproduced, and the layer was reconciled from this project's own design corpus rather than from the standard document
