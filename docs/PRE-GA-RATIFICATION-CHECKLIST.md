# Nami Pre-GA Ratification Checklist

Every accepted ADR builds a **mechanism**; several defer a **policy, threshold, or sign-off** to a human owner (DPO, Legal, Security, Ops, Product) before general availability. This file consolidates those into one release gate. The ADR remains the source of each decision; this is the tracking index. **GA is blocked until every item below is ratified** (recorded with date and approver). Interim values may ship in pre-GA builds where an ADR marks them interim. This project builds mechanisms and does not itself assert legal compliance.

**Status key:** ☐ open · ☑ ratified (date, approver)

- ☐ Erasure: whether crypto-shred satisfies Art.17; audit retention plus per-record Art.17(3) basis; legal-hold workflow; anonymise-in-place interpretation; Recital-66 replica retention ([ADR-0016](adr/0016-right-to-erasure.md))
- ☐ Data-subject rights: Art.12 SLAs; Art.15 source/automated-decision wording; portability direct-transmit yes/no; Art.34 high-risk threshold plus jurisdiction authority/deadline; Art.30 content; DPIA execution; consent policy-version governance; Art.18 scope plus Art.21 legitimate-interest balancing ([ADR-0053](adr/0053-data-subject-rights-suite.md))
- ☐ Cross-border / residency: per-tenant residency classification; lawfulness and mechanism of each transfer; transfer-assessment content and filing; Law-on-Data core/important-data export path if applicable ([ADR-0054](adr/0054-cross-border-transfer-and-data-residency.md))
- ☐ Source-address pseudonym in the audit lane: whether persisting `SourceIpHash`, a keyed untruncated HMAC over the request address, is acceptable under the applicable basis. The architecture is decided and the legal question is deliberately not: the field is nullable and its emission configurable, so a refusal is a configuration answer. **Detection does not depend on this**, because per-address evaluation runs in a bounded in-memory window that stores nothing, so a refusal costs durable cross-node *attribution* and not the capability. **Bounded here is measured, not asserted**: the design corpus's spike A-11 held the window at its ten-thousand cap across two million distinct addresses (verification record V30, 2026-07-29), which matters to this decision because an unbounded window would have made the fallback worse than the thing it replaces. **A second question on the same field, added 2026-08-02 while ratifying the audit-export bounds**: whether `SourceIpHash` may additionally **leave the console** in a bulk audit export, to an external auditor, a regulator, or a tenant assembling evidence. It is not implied by the first. `SourceIpHash` is in the canonical hashed field set from genesis (design [03](design/03-audit.md) section 3), so the export carries it by construction, and dropping it would leave the recipient unable to verify the chain, which is the only reason [ADR-0008](adr/0008-audit-subsystem.md) ships an export at all. So the options are not persist-or-not but export-with-it, export-without-it-and-lose-verifiability, or a third mechanism nobody has designed. **The answer to the first question does not settle this one in either direction**: a refusal to persist makes it moot, but a permission to persist says nothing about disclosure to a third party ([ADR-0082](adr/0082-abuse-detection-lanes-and-grouping-keys.md), with [ADR-0083](adr/0083-abuse-detection-is-built-in.md) and [ADR-0008](adr/0008-audit-subsystem.md))
- ☐ Telemetry / registration: telemetry data categories (no PII); registration PII retention; privacy notice; registration terms ([ADR-0032](adr/0032-usage-visibility-and-licensing-posture.md))
- ☐ HIBP breach-check: sending a hash prefix to an external service (DP.01) ([ADR-0028](adr/0028-user-management.md))
- ☐ Consent re-prompt cadence: whether a granted consent must expire and be re-asked periodically. ADR-0004 deliberately leaves consent lifetime unbounded (an OpenIddict permanent authorization persists until the user revokes it), so bounding it is a policy call, not a build gap. If it is required, the mechanism is an expiry stamped on `Authorization.Properties` plus a prune ([ADR-0004](adr/0004-refresh-token-posture.md))
- ☐ Deprovision key-escrow retention window and residency ([ADR-0017](adr/0017-tenant-provisioning-and-silo-migration.md))
- ☐ Change-event publishing (v2): PII in event payloads flowing to the broker and its consumers, the outward data flow, and event retention (DP.01) ([ADR-0071](adr/0071-identity-change-event-publishing.md))

- ☐ Browser-facing header residuals: the enumerated `Permissions-Policy` allowlist, which ADR-0091 fixes only as a deny-by-default posture because the concrete feature identifiers depend on what the passkey path needs; and acceptance of `img-src 'self' https:` on the login page, which admits any https origin as an image source so tenant and client logos render, rather than proxying them through Nami and widening the SSRF surface that the render-time logo guard exists for. The framing, script, and style directives need no ratification: each is `'none'` or `'self'` with a startup invariant behind it ([ADR-0091](adr/0091-browser-facing-response-headers.md), with [ADR-0028](adr/0028-user-management.md) for the passkey feature list)
- ☑ How the UI response profile reaches pages Nami did not write (**2026-08-02, Nam Phuong Tran as security lead**; recorded as [ADR-0091](adr/0091-browser-facing-response-headers.md) parameter K and a third [ADR-0043](adr/0043-security-hardening-invariants-startup-check.md) invariant). The item read: [ADR-0027](adr/0027-packaging-and-distribution.md) parameter G ships no UI package, so an embedder writes their own login page, and the UI profile is selected by a `SecurityHeadersAttribute` that reaches only the pages it is applied to; the failure mode is a third party's login page served with no policy while every ADR-0043 startup check still passes, since those checks assert what the profiles contain and not which pages receive them. **Ratified as: the header middleware writes a profile on every response, endpoint metadata only selects which one, absent metadata means the UI profile, and leaving the policy requires an explicit opt-out**, with a `response-headers-registered` startup row for the consumer who never registers the middleware at all. Two things are worth carrying forward from how it closed. **The item as written located the fault in the wrong place**: the attribute's reach is the second-order effect, and the first-order fact is that ADR-0091 parameter B's three `Applies to` cells all enumerate surfaces Nami authors, so the partition stopped being total on the day parameter G was accepted, which was the same day that ADR was. **And the three options offered here omitted the one this repository already had a precedent for**: they were documentation, a default, or a startup *warning*, while ADR-0043's `hsts-enabled-outside-dev` row had been asserting that a middleware **is registered** since 2026-07-26, making a startup *failure* available and unlisted. What is signed off is therefore not one of the three options as stated
- ☑ Audit-export bounds (**2026-08-02, Nam Phuong Tran as security lead**; recorded as a fifth [ADR-0008](adr/0008-audit-subsystem.md) bulk-export sub-parameter and a correction to [ADR-0081](adr/0081-dual-control-target-guard-taxonomy.md)'s `query` guard). The item asked for two numbers, an absolute cap on rows or time span, and a drift tolerance between approval and redemption. **Neither was signed, because neither is a number Security can usefully own.** A cap is defeated by looping under it while every export is dual-control regardless of size, so it bounds nothing; the real reason to limit a redemption is that it is one unbounded streaming read over a hot append-only table, which is an [ADR-0040](adr/0040-resiliency-and-overload-protection.md)-family engineering limit. And the drift was **removed rather than tolerated**: the frozen filter must now carry an absolute upper time bound, so the record set is closed at freeze, and a guard failure at redemption is terminal. Three things found while closing it are worth keeping. **ADR-0081's guard was re-evaluating a threshold that no longer existed**: its wording came from the corpus, where a size threshold decided whether dual-control applied at all, and ADR-0008 removed that path on the same date without the guards that named it being re-read. **This entry's own supporting argument was half wrong**: the claim that "the same egress is reachable by paging `GET /audit`" does not hold, because `AuditEntryDto` carries eight fields and no hashes while the export carries the per-row hashes plus the canonical fields, which include `SubjectRef`, `SourceIpHash`, and `ClientId`; the export is a strictly larger disclosure per row, and the conclusion survives on the looping argument alone. **And the corpus asked a narrower version whose answer its own decision record already carried**: ratify packet SEC-A4 puts three options to Security with the decision line blank, while the corpus guard-taxonomy decision record rules `precondition_failed` for create and query "terminal and single-use" forty-six lines above the paragraph asking whether query should warn instead. Two of the three options were foreclosed by the document offering them. Hard failure is chosen, its option (a), for consistency rather than for severity
- ☐ Formal cryptoperiod (ISMS sign-off, with Ops): the signing, encryption, and retention periods stated as policy with a named owner. The build implements ADR-0011's 90/14/14; this ratifies it as the recorded cryptoperiod ([ADR-0011](adr/0011-no-restart-key-rotation.md), [ADR-0005](adr/0005-encryption-credential-lifecycle.md))
- ☐ Authorization SLO / timeout (with Ops) ([ADR-0047](adr/0047-authorization-decision-engine.md))

- ☐ Change-event publishing (v2): per-consumer bus access control; whether configuring the broker connection is an IAM-class change requiring dual-control; thin-versus-fat payload for PII minimization ([ADR-0071](adr/0071-identity-change-event-publishing.md))
- ☐ BFF package shipped defaults: the cookie lifetimes the package ships (a sliding window plus an absolute cap, both consumer-tunable), which are legitimately allowed to exceed the OP's own 8-hour absolute session because the RP session is a separate object, so the number is a policy choice rather than a consequence of ADR-0003; and whether `POST` plus an antiforgery token replaces the session-bound `sid` query parameter as the shipped default on `/bff/logout`. - ☑ Workflow-definition analysis (**2026-08-02, Nam Phuong Tran as security lead**; recorded as [ADR-0092](adr/0092-ci-security-scan-tooling.md) section 6 and two new rules in `scripts/check-adrs.sh`). The item offered two ways out, accept the risk or buy a sixth tool with a sixth licence, and said it was not an architect's pick because the alternative to accepting was a permanent dependency for the smallest of the five surfaces. **A third way was available and unlisted**, and it is the argument ADR-0092 had already won once: a capability this project already runs costs no licence. The guardrail that gates every commit gained two bright lines instead, no `${{ }}` inside any `run:` script and no `pull_request_target` or `workflow_run` trigger, chosen because neither needs a judgement about which inputs are trusted; the first enforces the standard mitigation, passing values through `env:`, rather than trying to classify a value as dangerous. **Measuring first changed what was being decided**: on that date the whole `.github/` tree held zero expressions of any kind, zero such triggers, two literal `run:` steps, `permissions: contents: read`, and every action SHA-pinned, so a tool bought then would have found nothing. **Two of those readings were overtaken later the same day and the measurement is left as it was taken**, since a dated measurement that gets edited to match today stops being evidence: a third action (`actions/setup-dotnet`) arrived with the solution build job, and ADR-0086 parameter A was reversed, so the pins are now full version tags rather than SHAs. Neither movement touches what this item decided. What makes the gap real is M1, when the release pipeline puts `id-token: write` on a job and four more scan stages become workflow steps, and Dependabot already opens weekly pull requests against the workflow directory. **Read the scope, not the green**: the rules cover two constructs and not workflow safety, and `with:` interpolation, `permissions:` scope, and reusable workflows in other repositories are all outside them. The reversal condition is recorded and **no candidate tool is named**, because no licence has been read for one and naming it would make an open search look like finished research ([ADR-0086](adr/0086-pin-ci-actions-by-version-tag.md) remains the adjacent decision, governing which action code runs)
- ☐ OWASP ASVS 5.0 Level 2 self-assessment coverage complete (L3 for key/token/dual-control/tenant-isolation), API Security Top 10 mapped ([ADR-0062](adr/0062-owasp-asvs-security-baseline.md))

- ☐ **Row-level-security role verification in every deployed environment**: confirm the runtime database role is `NOSUPERUSER` and lacks `BYPASSRLS` ([ADR-0037](adr/0037-database-engine-postgresql.md)). - ☐ **Confirm the external-tool licences that the CI licence gate cannot see** ([ADR-0026](adr/0026-dependency-license-policy.md), [ADR-0078](adr/0078-load-test-tooling.md)). ADR-0026 section C's scan reads the NuGet restore graph, so **every external tool is invisible to it** and the gate's silence is not evidence of compliance. This is structural, not a bug to fix in the scanner. The tools in this class are the four `execute-only` rows in section 2 of [`DEPENDENCY-LICENSES.md`](DEPENDENCY-LICENSES.md), each with its verification source and date: Apache JMeter, the OIDF conformance suite image, cosign, and the CycloneDX dotnet tool (the last two added 2026-08-02, which is why an earlier version of this entry named only the first two). Legal confirms the list is complete for the distribution model and that none of these tools is conveyed inside a shipped artifact (the reference host image, the Helm chart, the NuGet meta-package, the `dotnet new` template), since bundling a tool changes the question from execution to conveying. **Rewritten 2026-08-02, because the sentence that stood here was verified false.** It read "no AGPL or copyleft question remains open here ... this entry is an inventory confirmation, not a legal judgement call", on the reasoning that k6 had been removed for being AGPL rather than carved out (ADR-0078). Enumerating JMeter's own released bundle at 5.6.3 found **nine components outside ADR-0026 section A's permissive set**, including `MPL-2.0`, `EPL-1.0`, `CDDL-1.0`, `CC-BY-SA-3.0` and one `CDDL-1.0 AND GPL-2.0-or-later WITH Classpath-exception-2.0`, listed by name in section 2.1 of that file. **No AGPL, verified.** So what Legal is asked is a judgement and not a tick: confirm that running an unmodified tool as a separate process against Nami's own service, and shipping none of it, leaves each of those nine answerable as execution rather than conveying. Six of the nine fell into **none** of section A's three buckets when this was found, which was a gap in ADR-0026 rather than in any tool; ADR-0026 closed it the same day with a residual rule (a licence in no list means the dependency is not taken) plus a scope statement (the lists classify what Nami conveys, so a component inside an `execute-only` tool is answered by the section C boundary). That is what makes the question above answerable as a boundary question rather than a per-licence one. The other three rows have not been enumerated yet; section 7 of the licence record names where each declares its composition, and the enumeration is owed when a version is pinned.
- ☐ **One IP-lawyer review of the public docs before public launch** (standing recommendation). In scope, among the rest: the architecture layer follows the **arc42** template's chapter sequence and credits it in [`docs/architecture/README.md`](architecture/README.md). arc42 is CC BY-SA 4.0, whose ShareAlike term attaches to adaptations of the licensed material; this repository reproduces none of arc42's text, explanations, or diagrams and adapts the chapter set, so the position taken is that the documents are not adaptations and remain Apache-2.0 with the credit given as attribution. That position is worth one lawyer's confirmation, not a redesign. **The same question applies to the detailed-design layer**, whose section sequence follows the **IEEE 1016** software-design-description viewpoints, credited in [`docs/design/README.md`](design/README.md). IEEE 1016 is a paid standard rather than an openly licensed one, so the position is narrower and worth stating: only the viewpoint vocabulary and the section ordering are used, no standard text is reproduced, and the layer was reconciled from this project's own design corpus rather than from the standard document
