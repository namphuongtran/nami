# Build a Nami.Identity.Bff package by composing OSS-permissive pieces rather than adopting a commercial BFF

## Context and Problem Statement

A commercial identity vendor sells a commercial backend-for-frontend (BFF) package for SPAs: server-side tokens, automatic/silent renewal, anti-forgery, a backend proxy, session, and logout. Nami wants parity for consumer SPAs but as OSS. Research on 2026-07-04 confirmed that the commercial BFF package carries a paid production license, so it is rejected under ADR-0026. Nami already uses a BFF *pattern* for the admin app (ADR-0020) and recommends a BFF for SPAs (a non-extractable key does not stop XSS, so the BFF is the real mitigation), but it has no reusable BFF package for consumers. How should the BFF be provided?

## Decision Drivers

* Parity with a commercial BFF, but OSS and free.
* The token must never reach the browser, which is the real XSS mitigation for SPA and mobile-web clients.
* Reuse one BFF for both the admin app and consumer SPAs.
* Give consumers a secure default out of the box.

## Considered Options

* Adopt the commercial BFF package
* Build `Nami.Identity.Bff` by composing OSS-permissive pieces (YARP, `Duende.AccessTokenManagement.OpenIdConnect`, and ASP.NET cookie/OIDC/antiforgery)
* Ship no BFF and leave it to the consumer

## Decision Outcome

Chosen option: "Build `Nami.Identity.Bff` by composition", at parity with a commercial BFF but from permissive pieces (several already used elsewhere in Nami), because the commercial package is rejected by the OSS-only policy and leaving it to consumers risks them putting the token in the browser.

* **A. Components (composed from OSS-permissive pieces):**

  | Feature | Built from | License |
  |---|---|---|
  | Server-side token storage plus automatic/silent renewal | `Duende.AccessTokenManagement.OpenIdConnect` 4.2.0, the interactive-OpenID-Connect package, over ASP.NET Core's built-in OIDC token handling (settled in ADR-0026 sections D and E) | Apache-2.0 |
  | Backend API proxy (local and remote) | YARP | MIT |
  | Anti-forgery (CSRF), in two profiles | a server-rendered admin form uses an ASP.NET antiforgery token; a JS/SPA proxy uses a custom header plus strict CORS plus rejecting the CORS-simple content type | MIT |
  | Session | a `__Host-` HttpOnly/Secure/SameSite cookie plus a server-side session (ADR-0003) | MIT |
  | Logout (plus back-channel) | ASP.NET OIDC sign-out plus a back-channel logout receiver (ADR-0019) | MIT |

* **B. Security principles (consistent with ADR-0019/0020/0024):**
  * The token **never** reaches the browser (an httpOnly cookie holds the session, and the access/refresh tokens stay server-side) which is the real XSS mitigation for SPA and mobile-web (a non-extractable key is not enough).
  * Anti-forgery is mandatory on every state-changing call, in two profiles: a server-rendered admin form uses an antiforgery token, and a JS/SPA proxy uses a custom header plus strict CORS plus rejecting the CORS-simple content type (a custom header alone is bypassable by a simple-content-type cross-site form POST, so a content-type guard plus strict CORS are required).
  * The BFF proxy forwards only to an allow-listed backend and attaches the bearer server-side.
* **C. Packaging (ADR-0027):** `Nami.Identity.Bff` (plus a `.Bff.Yarp` for the remote proxy, split as the commercial product splits it) is enabled by a consumer via `services.AddNamiBff()...`. `Nami.Identity.Admin.App` (ADR-0020) is refactored to use this same package, giving one BFF with two consumers (the admin app and consumer SPAs) and no duplicated code.
* **D. Scope boundary.** This BFF covers browser-SPA and mobile-web clients, where the token stays server-side. Token management for a resource-consuming RP or worker (a service calling downstream APIs with its own client-credentials tokens) is **out of the batteries-included surface**; integrators add `Duende.AccessTokenManagement` (the base, client-credentials-oriented package, Apache-2.0) directly, with an optional thin machine-to-machine sample. Note that the two cases take **different packages of the same family** and this is not a redundancy: `.OpenIdConnect` exists for the interactive user-token case above and depends on the base package, whereas a worker with no interactive user needs only the base. The source project used one name for both, which is imprecise rather than wrong.

### Consequences

* Good, because it is at parity with a commercial BFF but OSS and free (the Apache-2.0 release of ADR-0027), reuses pieces Nami already has, and serves both admin and consumers from one BFF.
* Good, because a consumer SPA gets the correct XSS mitigation out of the box (the token is not in the browser).
* Bad, because there is no OSS drop-in, so Nami must compose and maintain it (a medium-to-large effort), with the anti-forgery, proxy, and session paths needing careful testing.
* Bad, because it depends on the YARP and access-token-management versions, which calls for a contract-regression check when they are bumped (the ADR-0021 thinking). ADR-0040 rule A1 also applies: the token-management package registers its own retry-only pipeline on its own named clients, so the standard resilience handler must not be layered onto them.

### Confirmation

* The commercial BFF's feature set is documented, and its license is commercial, so it is rejected under ADR-0026.
* The OSS fill is available and verified: YARP (MIT), `Duende.AccessTokenManagement.OpenIdConnect` 4.2.0 (Apache-2.0, ADR-0026 section D), ASP.NET cookie/OIDC/antiforgery (MIT), and Microsoft's `BlazorWebAppOidcBff` sample as the reference pattern.

## Pros and Cons of the Options

### Adopt the commercial BFF package

* Good, because it is a turnkey, well-supported drop-in.
* Bad, because it carries a paid production license and is rejected by the OSS-only policy (ADR-0026).

### Build `Nami.Identity.Bff` by composition (chosen)

* Good, because it reaches parity from permissive pieces (many already used), stays OSS/free, and yields one BFF for both admin and consumers.
* Bad, because it must be composed and maintained rather than dropped in, and the security-sensitive paths need careful testing.

### Ship no BFF and leave it to the consumer

* Good, because it is the least for Nami to build.
* Bad, because it loses developer experience and risks consumers implementing it insecurely, with the token ending up in the browser.

* Original decision 2026-07-04 (the shape accepted, with build-time picks still open).
* This BFF is the acknowledged composition boundary in ADR-0024 (a deliberate exception to the ports-at-the-edge rule, since it has no port).
* Build-time follow-ups: the `/bff/login|logout|user` endpoints plus the `/api/*` proxy (YARP) plus anti-forgery plus the back-channel-logout receiver; refactoring the admin app to share this package; and deciding whether to split `.Bff` from `.Bff.Yarp` (the remote proxy) or ship one package.
* Related decisions: ADR-0003 (the server-side session), ADR-0019 (the BFF stance and back-channel logout), ADR-0020 (the admin BFF that uses this package), ADR-0024 (the hexagonal style, where this BFF is the acknowledged composition boundary rather than a port), ADR-0026 (the OSS-only policy that rejects the commercial BFF and settles the token-management packages in sections D and E), ADR-0027 (packaging and the `AddNamiBff` builder), and ADR-0040 (rule A1, the retry-stacking prohibition on the token-management named clients).
* Imported into this repository and translated in 2026-07; content preserved, internal references generalized. The access-token-management packages are named in full, per ADR-0026 section E: an earlier import generalized them under a "non-vendor-branded" wording that this project never actually decided, and a dependency record that hides a package identifier cannot drive the ADR-0026 license-scan gate. The product-name placeholder was set to `Nami.Identity.Bff`; note that the source's `services.AddNami.IdentityBff()` was an artifact of substituting a product placeholder, and `AddNamiBff()` is the correct form here.
