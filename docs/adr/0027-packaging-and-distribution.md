# Distribute Nami as a hybrid NuGet meta-package plus a reference host image and template, released under Apache-2.0

## Context and Problem Statement

The design is detailed to production level. The requirement is to release Nami as OSS for the community, as easy to adopt as a commercial identity server: a consumer adds a package with minimal config ("have a key and it runs") and it is monitorable out of the box. The question is whether to package it as a library or as a deployable product.

The positioning insight is that Nami builds **on** OpenIddict (the protocol library) and therefore does not re-implement the protocol from scratch. Nami's value is the opinionated, batteries-included layer on top: multi-tenancy, delegated-admin, no-restart rotation, admin, cloud-agnostic adapters, observability, and config developer-experience. So the positioning is a batteries-included distribution on top of OpenIddict, closer to an OpenIddict framework module or a .NET app-host stack than to a from-scratch server. The already-decided architecture (hexagonal ports in ADR-0024, cloud-agnostic ports in ADR-0006/0009, the auto-seed key in ADR-0012, and built-in OpenTelemetry in ADR-0022) already enables exactly this.

## Decision Drivers

* Easy adoption: add a package with minimal config, "have a key and it runs", monitorable out of the box.
* Serve both embedders (a library) and turnkey deployers (an image).
* Community OSS, free, with no paid gates.
* The value is the opinionated layer on OpenIddict, not a protocol re-implementation.

## Considered Options

* A pure library (NuGet plus `AddXxx()`, consumer self-hosts)
* A pure deployable (a container image plus Helm)
* A hybrid (a meta-package plus a fluent builder, plus a reference host image and a `dotnet new` template)

## Decision Outcome

Chosen option: "The hybrid", released under Apache-2.0, because the same core then serves both an embedder and a turnkey deployer, satisfying both "add a package" and "have a key and it runs, monitorable". A pure library fails "deploy and it runs", and a pure deployable fails "embed as a package".

* **A. Core: a NuGet meta-package plus a fluent builder (commercial-grade DX).** Ship a meta-package `Nami.Identity` plus granular sub-packages so a consumer takes only what it needs (mirroring how OpenIddict splits packages). A fluent builder, `services.AddNamiIdentity(cfg)...`, has safe defaults like `AddOpenIddict()`, with the minimal config being a connection string and an issuer. "Have a key and it runs" comes from auto-seed (ADR-0012, the Database provider), so no key is provisioned by hand. "Monitorable" comes from built-in OpenTelemetry (ADR-0022), so wiring up OTLP just works. Package versions are generated from a single git tag by MinVer (a permissive-licensed tool), yielding one lock-step version across the whole package graph; ADR-0044 governs what may change under that version, and ADR-0030 uses the same tool for multi-target versioning.
* **B. Reference host: an image plus Helm plus a template (deploy-and-it-runs DX).** The reference host is a named application project, **`Nami.Identity.Host`**, and it is deliberately **not** a NuGet package (`IsPackable=false`, ADR-0065): it is distributed as a container image and as a `dotnet new` template. Keeping it separate from the `Nami.Identity` meta-package is what makes both stories unambiguous, since a meta-package is by construction an empty project carrying only package references while a host carries an entry point, configuration, a Dockerfile, and health endpoints. It is also what makes the end-to-end tests meaningful: the integration and browser suites exercise **the host that ships** (ADR-0060), and the container tests run the image that ships (ADR-0025), rather than a host the test project assembled for itself. A chiseled container image (ADR-0025) runs the IdP and Admin, configured via environment variables, in a multi-mode entrypoint (`serve`, `migrate`, `export`, and `prune`; the `prune` mode exists because ADR-0031 keeps the bulk token and authorization prune off the request-serving path rather than co-hosting it). A `dotnet new nami-identity` template scaffolds a customizable host. A Helm chart covers Kubernetes (production IaC is OpenTofu, ADR-0023). A bootstrap-admin path applies a `Bootstrap__Admin*` environment configuration once at first start (when no admin exists), with a forced password change, an audit entry, a tie to the ADR-0015 first-admin bootstrap (and to nothing in ADR-0007: that ADR is break-glass for a *compromised key*, a different concern, and the source corpus cross-referenced it here inconsistently), and a fail-fast in Production, parity with the bootstrap-admin mechanisms of mainstream OSS identity servers (Keycloak's `--bootstrap-admin-*` flags and Zitadel's `FIRSTINSTANCE` configuration), giving a turnkey "run the container, then log in as admin". Declarative config import/export provides an idempotent, secret-free import (in `migrate`/init mode) covering clients, scopes, resources, Pool tenants and their memberships, claim-mappers, and CORS origins, upserting by concurrency token so it does not overwrite an operator's live edit unless forced (a rule this ADR owns, since the import/export feature is defined here; the separate environment-over-file config-precedence chart is ADR-0031's), plus an `export` sub-command as a further entrypoint mode that dumps the current config (never secrets or keys); this enables "pull and run my setup" plus GitOps and backup, at parity with mainstream OSS import/export (Keycloak's `--import-realm` and export, and Zitadel's `steps.yaml`). Keycloak's separate `build`/`--optimized` step is not applicable to .NET, since publish-time already optimizes, so Nami's mode set stays the four above.
* **C. Release license: Apache-2.0.** It matches OpenIddict, is permissive, and carries a patent grant that matters for a security product, so the community can use it freely rather than paying. This is distinct from ADR-0026, which governs the licenses Nami *consumes*; this is the license Nami *releases*. There is no dual-license commercial tier, keeping Nami purely OSS in line with the "for the community" intent.
* **D. Public-API stability discipline (a library's survival condition).** The public API is treated as a versioned seam with strict SemVer, an analyzer-locked surface, and a staged deprecation policy. This is the ADR-0021 seam-catalogue thinking applied to Nami's own API, since a consumer is downstream of Nami exactly as Nami is downstream of OpenIddict. The full policy is recorded in ADR-0044 (public-API stability and SemVer) and is not restated here.
* **E. Extension model for consumers: the ports (ADR-0024).** The hexagonal ports (key store, secret resolver, tenant store, audit sink, email dispatcher, the ReBAC `ICheckAccess`, and so on) are documented extension points, so a consumer swaps an adapter (for example a key store to Vault) without forking the core.

  **UI customization is a documented extension point too, added 2026-08-01, and what it offers depends on the distribution channel.** Neither mechanism is a view-override, because parameter G ships no UI class library. The first is **configuration**: logo, colour, and display name arrive as configuration and environment keys, which works on every channel because it is read at runtime rather than resolved against files on disk. The second is **source ownership on the template channel**: parameter B's template "scaffolds a customizable host", so the scaffolded `.cshtml` files and the `wwwroot/theme/` assets folder belong to the consumer, and editing them is the sanctioned mechanism rather than a fork. Both the configuration keys and the asset paths are a versioned surface under ADR-0044 parameter I, which is what stops "documented extension point" from meaning "stable by habit". Per-tenant branding is a different thing and **not** an extension point: it is product data on `TenantBranding` reaching the browser as a served stylesheet (ADR-0091 parameter D), administered rather than deployed. **One question is left open rather than answered here**: how an operator on the container channel replaces a shipped asset, since the image carries `wwwroot` baked in and neither ADR-0025 nor design [21](../design/21-cicd-and-deployment.md) records a route to it. That absence carries its method, because an absence is only as good as the pattern behind it: searching both documents for `volume`, `mount`, `bind`, `overlay`, `COPY`, `static file`, `StaticFiles`, and `asset` returns a PostgreSQL data volume and a development certificate mounted from a file, and nothing about replacing a shipped asset. That is a deployment mechanism rather than a packaging one, so it belongs with the deployment design, and until it exists **the container channel offers configuration only**.
* **F. OpenID certification path and target profiles.** Nami self-certifies a stable reference-host at specific OpenID Provider profiles rather than an abstract library (certification is per host, config profile, and version). The target set is OP Basic, OP Config, and OP FormPost, following the protocol scope of ADR-0014; Hybrid/Implicit is certified only if a client needs it, Dynamic (DCR) is deferred until OpenIddict ships it natively (8.0), FAPI 2.0 is not targeted (its message-signing profiles are de-scoped in ADR-0014), and back-channel-logout and DPoP/mTLS conformance follow once each is stable and proven. The OpenID Foundation conformance suite already runs in CI on the reference-host profile so it stays green before any submission, and re-certification is done on a major version or a protocol-affecting change. Certification is a pre-public-release step, not an MVP blocker. One precondition is open: certification needs a stable public reference-host, and whether to stand one up (owner, hosting, patch cadence, cost) or to certify local-Docker-only is pending Ops ratification.

* **G. The human-facing pages ship in the host and in no package, so an embedder supplies its own (added 2026-08-01).** The Razor Pages login, consent, logout, passkey, account-management, and error surface (ADR-0072) lives in `Nami.Identity.Host`, which parameter B makes `IsPackable=false`. **No `Nami.Identity.UI` Razor Class Library is shipped**, and that is a decision rather than an omission. A class library is the only shape in which "a consumer view wins over the default by view-engine precedence" is a real mechanism, and it would make every view path and view name a consumer-facing compatibility surface; ADR-0044 parameter A locks the public surface with an analyzer that sees public types and members, not `.cshtml` paths, so the one mechanism that would police that surface is structurally blind to it. The consequence is therefore stated here rather than left to be discovered: a consumer who adds the meta-package to their own application supplies the interaction pages themselves, including the login route that the pass-through authorize endpoint challenges to, which design [11](../design/11-login-consent-ui.md) section 3.1 names `/Account/Login`. This mirrors OpenIddict, which ships no user interface either (ADR-0072). "Add a package with minimal config" in the drivers above is accordingly a claim about the **server**, not about the pages a human sees, and turnkey is unaffected, since the container image and the `dotnet new nami-identity` template both carry those pages. Revisit if the embedder path is ever promoted to a supported UI surface, in which case the library and a view-path compatibility policy are one decision and not two.

### Consequences

* Good, because it satisfies both "add a package" and "deploy and it runs, has a key, and is monitorable"; it is both embeddable and turnkey; it is free for the community (Apache-2.0); and consumers extend it through ports rather than forks.
* Bad, because the embedder story stops short of the human-facing pages: parameter G ships them only in the host, so an embedder builds its own login, consent, and logout pages. Accepted 2026-08-01 as the cheaper side of the trade, because the alternative turns view paths into a compatibility surface that the ADR-0044 analyzer cannot see.
* Good, because the current architecture is already ready (ports, auto-seed, OpenTelemetry), so productization is packaging and polish rather than a rewrite.
* Bad, because maintaining a library is heavier than an internal app: public-API stability (SemVer plus the analyzer), docs and samples, versioning discipline, and community support, which need a governance/security policy and a CI publish pipeline.
* Bad, because there is no dual-license, and therefore no license revenue, which is traded for adoption and the OSS spirit.

### Confirmation

* OpenIddict and commercial identity servers both ship via NuGet package splits; a .NET framework module and an app-host stack are the hybrid precedents (packages plus a template/host); and the "put the IdP in a separate app" guidance supports a reference host. The public-API analyzers are the Microsoft-recommended way to hold API stability, and the Apache-2.0 patent grant is standard for security OSS.
* The `dotnet new nami-identity` scaffold and the container image both serve the login, consent, and logout routes, and the meta-package carries no `.cshtml` at all, which is checkable from the published package contents rather than from a claim (parameter G).
* Approach settled 2026-07-07: the reference-host distribution (image/compose/Helm/template), the supply-chain measures (signing, SBOM, SLSA, scanning; detailed in ADR-0051), the bootstrap-admin, and the declarative config import/export are the decided approach; only build-time sub-details remain (final environment-variable names, the import format JSON versus YAML, and the template option set), which are not open decisions.

## Pros and Cons of the Options

### A pure library

* Good, because it is the simplest to embed.
* Bad, because "deploy and it runs" is not met; the consumer must build and operate the host.

### A pure deployable

* Good, because "deploy and it runs" is met out of the box.
* Bad, because it cannot be embedded as a package into a consumer's own host.

### A hybrid (chosen)

* Good, because one core serves both consumer types and satisfies every adoption goal.
* Bad, because it is the most to build and maintain (both a package line and a reference host).

## More Information

* Original decision 2026-07-04; the reference-host distribution, supply-chain measures, bootstrap-admin, and declarative config import/export were confirmed on 2026-07-07.
* **Parameter G was added 2026-08-01**, prompted by a design-layer sweep that found design [11](../design/11-login-consent-ui.md) describing the UI's home as "the `Nami.Identity` reference host", which attaches the host label to the meta-package. The conflation was the visible defect; the decision it hid was whether an embedder gets pages at all, and nothing in the repository had answered it either way. Its own section 2 now records both.
* Build-time follow-ups: the final package graph, the fluent-builder API surface, the template scaffold, the docs site (which parameter G gives a specific obligation: the embedder path has to be documented as pages-not-included, or adopters will find it at runtime), the OpenID certification timing and profile set (F), including whether to stand up a public reference-host or certify local-Docker-only (Ops ratify), the CI publish pipeline (NuGet plus a container registry plus an SBOM per ADR-0026), and the governance/security files.
* **A second open consequence of parameter G, on the response headers, recorded 2026-08-01 rather than left between two ADRs.** ADR-0091 parameter A registers the header middleware in the fluent builder, "so the meta-package path gets them without the consumer knowing to ask", and that half is settled. The other half is not: design [11](../design/11-login-consent-ui.md) section 1 records that the **UI profile** is selected by a `SecurityHeadersAttribute`, and an attribute reaches only the pages it is applied to, so login pages an embedder writes themselves fall outside the UI profile unless the embedder applies it. This is not a defect in ADR-0091, whose parameter A reasons about a consumer writing their own *host*; parameter G is what makes the *pages* the consumer's too, which is new surface. Whether the fix is documentation, a default that applies the profile to the whole surface unless opted out, or something else is **not decided here**, and it is stated as open because the failure mode is a consumer's login page served with no policy at all while every startup check in ADR-0043 still passes, those checks asserting what the profiles contain and not which pages receive them.
* **An adjacent question parameter G exposed and does not answer: which assembly carries the five pass-through controllers.** Design [04](../design/04-core-protocol.md) fixes that authorize, token, userinfo, end-session, and end-user verification are pass-through, meaning each needs an application-supplied action, while device authorization, PAR, introspection, and revocation are fully handled natively. Searches for `AuthorizationController`, "authorize controller", and "endpoints live" across `docs/design/` and `docs/architecture/` return no statement of which assembly those five live in, so **how much beyond the pages an embedder must supply is not recorded**, and this is marked not verified rather than assumed either way. It resolves with the final package graph above rather than as a separate decision, and it is stated here so the package graph is written with the question in view.
